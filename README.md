# phone-privacy-audit

iPhone個人情報保護監査アプリ。

自分の端末とアカウント群を定期的に棚卸しするための、単一HTMLファイル（+ `support.js`）のセルフホスト型ツール。
想定しているのは、MullvadVPNを自ら選んで使うような、すでに知識と警戒心を持っている人。
啓蒙や説得のトーンではなく、業務監査ツールに近い無機質さを狙っている。

**ノーログ方針。** チェックリストの進捗・連携アカウント台帳・監査レベル・通知設定を含め、いかなる状態も端末内にすら永続化しない。すべて React state（メモリ上）のみで保持し、ページを閉じる・リロードすると初期状態に戻る。以前は「端末内には保存するが外部には送信しない」という設計だったが、専門性の高い想定利用者に対しては「記録が構造的に残りようがない」ことのほうが、宣言としてのノーログポリシーより説得力を持つと判断し、一段階踏み込んだ。`localStorage` への書き込みは一切行わない。ソースコードは全公開されているので、この宣言が本当かどうかは誰でも検証できる。

- `index.html` — アプリ本体（テンプレート＋ロジック＋内蔵データ）
- `support.js` — Claude Design ランタイム（生成物。編集しない）
- `settings-data.json` — 配信データ。**新着項目はこのファイルを書き換えて push するだけで反映される**

## 4本の柱

### 1. 設定状況確認

初回選択画面は **OS / アプリ / サービス** に分けて表示する。各アプリの `category`（`os` / `app` / `service`）で振り分けており、値が無い古いデータは `app` として扱う。

LINE・Google/Gemini・iOS 26・Instagram/Facebook・X・TikTok・Amazon/Alexa・ChatGPT・GitHub・Discord・WhatsApp・Yahoo! JAPAN・PayPay・VPN の
**14サービス・42項目**のプライバシー設定チェックリスト。

各項目に「設定パス」「なぜ重要か」「既定値はどうなっているか」を明記している。
X（Grok）へのデータ共有のように、**リロード後に設定が勝手にオンへ戻る既知の不具合**があるものは、項目ごとに注記フラグを立てている。

監査レベルで表示する重要度を絞り込める。**切り替えは初回選択画面だけに置く。** ホームにも歯車の中にも重複して置かない。変更したいときはヘッダーの「監査レベル・アプリ変更」から初回選択画面に戻る。初回選択画面では**監査レベルの選択をアプリ選択より上**に置き、直下に基本/標準/徹底の意味を箇条書きで常時表示する（選択中のものだけでなく3段階すべてを見比べてから選べるようにするため）。

| レベル | 表示される重要度 |
| --- | --- |
| 基本 | 要対応（high）のみ |
| 標準 | 要対応 + 推奨（high / medium） |
| 徹底 | すべて（high / medium / low） |

サブタブは **未対応 / 新着 / 済 / すべて**。チェックを入れた項目は「済」に移るので、そこでチェックを外せば未対応に戻せる。未対応タブだけだとチェックした瞬間に消えて取り消せなくなるため、この行き先が必要。

### 2. 連携アカウント台帳

パスワードは一切扱わない。「どのサービスに、どのアカウントでログインしているか」という **SSOの関係性だけ** を記録する台帳。

「LINEとYahoo!の連携解除は済んでいるか」「GitHubアカウントをWordPressに使っているか」といった結びつきを可視化する。

### 3. ネットワーク診断・自動測定

#### 項目は「判定を出せるか」で取捨する

**永久に「参考情報」しか返さない項目は置かない。** 判定が出ない項目が並ぶと、対応が必要な項目が埋もれる。17項目あった時点で5項目がこれに該当したため整理し、その後の第三者レビューでさらに2項目を整理して、現在11項目。

| 元の項目 | 処遇 | 理由 |
| --- | --- | --- |
| 出口ノード | IPv4 に統合 | colo は IPv4 の所在地とほぼ同じ情報。TLS 1.3 は現在ほぼ全環境。指紋対策ブラウザでは取得自体が失敗する |
| タイムゾーン整合性 | ブラウザ指紋に統合 | 指紋の一材料でしかなく、単独項目である必然性がない |
| トラッキング防止シグナル | ブラウザ指紋に統合 | DNT は事実上どのサイトも無視する。**送信すること自体が指紋の材料を増やす**ため、指紋の文脈で書くほうが正確 |
| トラッキング許可（ATT） | 削除 | 何も測れず設定への案内だけ。チェックリストの `ios-tracking` と完全重複 |
| **IPv4 アドレス／接続情報** | **VPN接続状態に統合** | 出口IPと登録組織名という同じデータを2枚のカードで別角度から見せているだけで冗長との指摘。判定を持つ側（VPN接続状態）に一本化した。カード名は「IPv4アドレス／VPN接続状態」 |
| **位置情報の許可（geoperm）** | **削除** | `Permissions API` で分かるのはこのページ単体への許可のみで、他アプリの許可状態（iOSのサンドボックスにより技術的に読み取り不可）と比べて情報量が乏しい。ダウングレード先のチェックリスト項目を追加する案もあったが、実機で確認していないパスを `verifiedAt` 付きで追加すると、この日付フィールドの意味（「実機で確認した日」）が嘘になるため、単純削除を選んだ |
| このアプリが端末に残しているもの | 削除 | 監査する側の自己開示として当初は残したが、利用者についての所見ではなく、総合評価にも入らない項目が増えると全体の見通しが悪くなるとの判断で撤去した |
| この診断で分かること・分からないこと | 削除 | 同上 |

現在の内訳は、判定を出す7項目（IPv6・DNS・WebRTC・トラッカー遮断・指紋・OS更新・サードパーティCookie）＋文脈2項目（IPv4・総合評価）。総合評価の集計対象は判定を出す項目のみ。**「前回からの変化（劣化検知）」項目は廃止した**——ノーログ方針への転換で、比較対象となる「前回の記録」自体を持たなくなったため（後述）。

**VPN接続状態の判定は廃止した。** 出口IPの登録組織名やDNSリゾルバの位置からVPN事業者を推定するロジックを一時期実装したが、「Webアプリでは推定でしかない」——ブラウザからVPN接続の有無を確定判定する手段がない以上、この推定は常に弱い根拠しか持てない——という判断で削除した。IPv4アドレス／接続情報は判定を持たない情報カードとして残し（出口IP・登録組織名・所在地・到達エッジ拠点の実測値のみ表示）、個別項目の先頭（総合評価の直後）に置く。ここが一番よく見られる項目になるため。

`Cloudflare trace` は `_fetchTrace()` で1回だけ取得し、IPv4カードのエッジ拠点／TLSバージョン表示に使う。かつてはVPN判定のWARP検出とも共有していたが、VPN判定自体を廃止したため今はIPv4カード専用。

#### 外部依存を隠さない

**診断ツール自身が何を外部に渡しているかを、利用者から見えない状態にしない。** 「あなたが何を漏らしているかを見せる」ツールが、自分自身の外部通信を隠していたら思想が一貫しない。診断結果・チェック状況・台帳の内容は一切送信しないが、診断のためにIPアドレスが外部サービスへ渡る項目は現に存在する。

各カードの見出し右に、外部照会か端末内完結かのバッジを付ける（`depBadgeOf()`）。1〜3社なら個別にドメイン名を列挙、4社以上（トラッカー遮断）は件数のみ表示する。ネットワーク診断画面の冒頭にも、渡る先の一覧を明記する。

| 項目 | 外部照会先 |
| --- | --- |
| IPv4アドレス／接続情報 | `api.ipify.org` / `ipwho.is` / `www.cloudflare.com` |
| IPv6アドレス／接続情報 | `api6.ipify.org` / `ipwho.is` |
| DNSリーク検査 | `edns.ip-api.com` |
| WebRTC IPリーク検査 | `stun.l.google.com`（ICE候補の収集に使うSTUNサーバー） |
| トラッカー遮断の実測 | Google・Meta・Criteo・Taboola（テスト対象そのもの。本文は読み取らない） |
| ブラウザ指紋／OS判定／サードパーティCookie | すべて端末内で完結 |

説明文の「外部には一切送信されません」という表現は誇張だったため、「診断結果の送信・保存は行いません。ただし診断のためIPアドレスが以下に渡ります」という正確な表現に改めた。**「送信しない」と書いてよいのは、本当に何も送っていないときだけ**にする。

#### 判定モデル（設計思想）

**断定は実測でしか行わない。** 直接測って確認できたものだけを「異常」とし、間接的な材料からの推定は「要確認」で止める。プライバシー診断では、漏れていないのに漏れて見える誤検知のほうが利用者の判断を歪める害が大きいと考えているため、**見逃しよりも誤検知を避ける側に倒している**。その代わり「要確認」を握りつぶさず必ず表示し、確信度を併記する。

全項目が共通の形式を持つ。

| 要素 | 値 |
| --- | --- |
| 判定 | 正常 / 要確認 / 異常 / 参考情報 / 判定不能 |
| 確信度 | 高（実測） / 中（推測） / 低（要追加確認） |
| 重要度 | 重大 / 中 / 低 |
| 根拠 | 「この判定になった理由」として必ず1行で表示 |
| 改善方法 | 対応が必要な場合のみ「【改善するには】」として付記 |

`_emit(id, {level, confidence, severity, text, rows, why, fix, note})` を通すことで、この形式を全項目で強制している。個別に `setState` を書かないこと——項目ごとに評価基準がばらつく原因になる。

先頭に**総合評価**（異常/要確認/正常の件数と、優先して直すべき項目）を置く。「この診断で分かること・分からないこと」項目（VPN事業者のログ保持・マルウェア感染・HTTPS傍受・他アプリの設定値・過去の漏洩が診断対象外である旨の注記）は撤去した。

**総合評価は他の項目とは見た目を変える。** 個別項目が破線1pxの枠なのに対し、総合評価は実線2pxの濃い枠・背景の濃淡・`SUMMARY` ラベル・判定を囲み罫で強調する。役割が違うもの（集計結果 vs 個別の測定）を同じ見た目で並べると、最初に見るべきものが埋もれる。実装上も `summaryCard` として `netChecks` から切り離しており、ループの中に混ぜない。個別項目の並びの前には「項目別の詳細」の見出しを置く。

**内訳は単一行のbadgeではなく、色分けした3行の縦積み（chips）で出す。** `_emit()` の通常の `text` は「`判定ラベル：本文`」という形式で結合されるため、総合評価に単純に `text:'異常 0 件／要確認 2 件／正常 5 件'` を渡すと「**要確認**：異常 0 件／**要確認** 2 件／正常 5 件」のように同じ語が1行に2回出て読みにくい（第三者レビューで指摘）。総合評価だけは `text:''` にして単一行badgeを出さず、`chips:[{label,count,color}]` を別途渡して「異常／要確認／正常」を改行し、赤 `VERDICT.risk.color` ／黄 `VERDICT.check.color` ／緑 `VERDICT.ok.color` で縦に並べる。

#### 指紋対策ブラウザを異常と誤判定しないこと

Mullvad Browser / Tor Browser は **UTC固定・画面サイズの丸め・GPU名の標準化・コア数の丸め**を仕様として行う。これを異常として表示すると、最も対策している利用者に最も多くの警告を出すという逆の結果になる。`_rfpHints()` で兆候を検出し、`rfpIsActive()` が「仕様とみなすか」を判定する。

**単純な個数しきい値（2つ以上）は誤検知を招く**——第三者レビューで指摘されたとおり、「UTCで運用しているサーバー管理者」＋「コア数2の古い端末」だけで2つの弱い信号が揃ってしまい、指紋が丸出しなのに仕様として見逃す事故になりうる。そこで信号を2段階に分けた。

- **決定的な信号**：GPU名の標準化（`Mozilla` 等）。実機の実GPUがこの値を返すことは通常なく、単独で「対策あり」と判定してよい
- **弱い信号**：UTC固定・画面サイズの丸め・コア数の丸め。それぞれ単独では正常な環境でも起こりうるため、**3つ揃って初めて**「仕様」と見なす

`rfpIsActive(hints) = hints.includes('GPU名の標準化') || hints.length >= 3`。WebRTCの候補0件、Canvasハッシュが前回と異なる（ランダム化）は、この判定とは別に、それぞれの項目内で個別に「対策が効いている」正常扱いにしている。

**「取得できる」ことと「識別しやすい」ことは別**。標準化（全員に同じ値）やランダム化（毎回違う値）が働いていれば、値が取れても識別には使えない。

#### DNSリークを組織名の不一致だけで断定しないこと

VPN事業者は複数のAS・データセンターにリゾルバを置くことがある。実際、Mullvad Browser で出口が `Owl Limited`（日本）、リゾルバが `M247 Europe SRL`（シンガポール）という組み合わせが観測された。**M247 はホスティング事業者であり、ISPへの流出ではない。** 組織名が違うというだけで「ISPに漏れている可能性」と表示するのは誤検知。

判定は強い順に、(1) 同一 /24 → 正常、(2) 組織名が一致 → 正常、(3) **リゾルバが `DATACENTER_ORG_RE` に該当 → 正常（重要度：低）**、(4) 一般ISPらしく別組織 → 要確認（断定はしない）、(5) 材料不足 → 判定不能。

#### ノーログ方針：状態は一切永続化しない

チェックリストの進捗（`done`）・新着の既読管理（`seen`）・選択したアプリ（`picked`）・監査レベル（`level`）・連携アカウント台帳（`accounts`）・配信データのキャッシュ（`data`）——**すべて `localStorage` に書き込まない。** コンストラクタは常にコード内のデフォルト値（`picked: null`、`done: []`、`level: 'standard'` 等）から始まり、`persist()` のような永続化関数自体が存在しない。ページを閉じる、またはリロードすると、すべての状態が消える。（通知設定・ウィジェットプレビューは機能自体を撤去したため、この一覧から除いた）

これに伴い、以前あった**「前回からの変化（劣化検知）」項目は廃止した**。この項目は `pa_history` に直近10回分の診断結果を記録し、判定ランクの変化を検出する仕組みだったが、比較対象となる「前回の記録」自体を持たなくなったため、機能の前提が成立しなくなった。設定が勝手に元へ戻る類の事故を継続的に検知したい場合は、確認のたびに手動で記録するしかない。

ブラウザ指紋の「Canvasのランダム化」検出だけは例外的に、同一セッション内（リロードしていない状態）での「再診断」ボタンの連打に限り、直前の実行結果とメモリ上（`this.state.prevCanvas`）で比較する。これは永続化ではない——リロードすれば消える一時的な比較用の値であり、`localStorage` は経由しない。

配信データ（`settings-data.json`）は起動のたびに `REMOTE_URL` から再取得する。取得できない場合（オフライン等）は内蔵の `APP_DATA` にフォールバックする。取得結果もキャッシュしない。

**設定値を読み取る項目**（IPv4/IPv6・DNS・WebRTC）に加えて、**実測して結果を出す項目**を持つ。前者は「何が観測できるか」、後者は「実際にどう振る舞っているか」を見る。

- **トラッカー遮断の実測** — Google Analytics / Meta Pixel / Criteo 等の既知トラッカーへ実際にリクエストを投げ、遮断されるかを測る。設定の読み取りではなく通信結果なので、コンテンツブロッカーの失効やドメイン単位の除外も含めて実態が出る。**`到達しなかった` は「遮断された可能性」であって断定ではない**——`mode:'no-cors'` の `catch` は、コンテンツブロッカーによる遮断・一時的な通信エラー・DNS失敗・相手サーバー障害のいずれかを区別できないため、文言を「遮断された」から「到達しなかった（遮断された可能性）」に修正した。重要度も、通過が1件でもあれば一律 `medium` にした（チェックリスト側でLINE/Metaのトラッキング関連項目を中〜高に分類しているのに、実測で通過が確認できている状態を「低」とするのは整合しなかったため）。
- **ブラウザ指紋の識別性** — Canvas描画・GPU名・フォント構成・画面情報などから、Cookieを消しても識別されうる信号がいくつ取得できるかを測る。母集団の統計は持たないため「何人に1人」という数値は出さない——出せば根拠のない数字になる。
- **OS・ブラウザの更新状況** — User-Agent から判定したバージョンを、配信データの `minVersions` と**メジャーバージョンのみ**で比較する。マイナー更新（26.0→26.1等）のたびに配信データを追随させないと、まだ更新していない大多数の利用者が一斉に要確認になる事故を避けるため。基準を下回るのは「まるまる1つ前のメジャーバージョン以下」の場合のみ。プライバシー設定をどれだけ詰めても、OSが古ければそこが最弱点になる。
- **サードパーティCookieの遮断** — ブラウザの種類（Safari/Firefox/Chrome系）と `document.hasStorageAccess` の対応状況から、サードパーティCookieが既定で遮断される構成かを推定する。**これは実測ではない。** 真の読み書きテストには別ドメインを使ったiframeが必要で、この単一ページアプリは第二のドメインを持たないため、新たな外部依存を増やしてまで実装するのは「外部依存を隠さない」方針と矛盾すると判断した。確信度は `est`（中：推測）と正直に申告する——実測できないものを実測と称さない。

**「このアプリが端末に残しているもの」（`_checkStorage`）と「この診断で分かること・分からないこと」（`_emitScope`）は撤去した。** 利用者についての所見ではなく総合評価の集計対象にも入らないため、項目数が増えるほど一覧の見通しを悪くするだけだった。ノーログ方針そのもの（`localStorage`に一切書き込まない設計）は変わらない——README冒頭とソースコードで検証できるが、アプリ内での実測による自己証明は現在は行っていない。

**1項目の例外で他が固まらないこと。** 各検査は `_safe()` で個別に包み、同期的に例外を投げるもの（指紋計算・保存量計測）も内部で `try/catch` している。`document` / `navigator` などのグローバルが欠けた環境でテストしても、全項目が完了することを確認済み（1項目だけ「判定不能」になり、残りは正常値を返す）。

設定値を読み取る側の項目は次のとおり。

- IPv4 / IPv6 アドレスと接続情報（ISP・登録組織名・おおよその所在地、エッジ拠点/colo・TLSバージョン）。判定は持たない
- DNSリーク検査（実際に名前解決を行ったリゾルバの特定）
- WebRTC IPリーク検査（ICE candidate の列挙）

**項目名と行ラベルは技術用語のままにする。** 「リゾルバ」「ICE candidate」「エッジ拠点 (colo)」「ATT」はそのまま使う。想定読者はこれらを知っている層なので、言い換えると逆に何を見ているのか分からなくなる。**平易さは説明文で担保する**——各項目の `desc` に、何を測っていて何が分かり、どういう値なら問題なのかを150字前後で書く。用語を薄めるのではなく、説明を厚くする。

**フィンガープリントの識別力を「何人に1人」のような数値で語らない。** 母集団の実測データを持たずに出せば、それは推測に過ぎない数字を確信度の高い数値のように見せることになる。（かつて `VPN_ORG_PATTERNS` という事業者名照合テーブルでVPN事業者名をUIに出す設計があったが、判定ロジックごと廃止した。特定事業者だけをUIで優遇しないという方針自体は、他の設計判断にも引き続き適用する。）

**IPv4の取得は必ずIPv4専用エンドポイント（`api.ipify.org`）を先に通す。** `https://ipwho.is/` に素で当てると「接続してきたIP」が返るため、端末がIPv6で接続しているとIPv4欄にIPv6が出る。さらにその値がWebRTC比較の基準になるので、比較が常に不一致になって誤報する。アドレスを確定させてから `ipwho.is/<ip>` で詳細を引くこと。

WebRTC検査は、上のIPv4診断が確定するのを待ってから比較する。並行実行のまま判定すると、取得前の値と比べて「別の公開IPを検出」と誤報する。

`bust()`（URLに時刻を付けてエッジキャッシュを外す）は**URLが毎回同じエンドポイントにだけ**使う。`ipwho.is/<ip>` はパスにIPが入るのでURL自体が変わり、不要。未知のクエリを受け付けないAPIに付けると失敗する（実際に一度壊した）。`cache:'no-store'` はブラウザキャッシュにしか効かないので、URLが固定のものには `bust()` が必要。

DNSリークの判定は**国ではなく組織名**で比較する（`orgToken()` で正規化）。出口が日本のVPNでリゾルバが日本のISPなら国は一致するが、それはまさに漏れている状態なので、国の一致を根拠にすると見逃す。判定の順序は上の「DNSリークを組織名の不一致だけで断定しないこと」を参照。材料不足を警告として出さないこと——漏れていないのに漏れて見えるのは、このツールでは最悪の失敗。

DNSリーク検査は `https://edns.ip-api.com/json` を使い、**実際に名前解決を行ったリゾルバ**のIPと所在地を取る（判定方法は上記）。dnsleaktest.com の拡張テストのように全リゾルバを列挙するには権威DNSサーバー側でログを取る必要があり、静的ページだけでは実施できない（旧実装は存在しない `dnsleaktest.com/api/v1/nameservers` を叩いていて常に失敗していた）。網羅的な確認はチェックリストの項目から dnsleaktest.com を直接開く運用にしている。

**診断は自動実行しない。** 明示的な「診断を開始する」操作を挟む。
WebRTC検査がOSの「ローカルネットワークへのアクセス」許可ダイアログを誘発しうるため、
ユーザーの能動的な操作の直後にしか出さない設計にしている。

### 4. 通知設定・ウィジェットプレビュー — 撤去済み

新着項目通知・定期リマインドのトグルと、iOS版ウィジェットのデザイン案プレビューを持っていたが、指示により削除した。いずれもこのWeb版では実際には動かない機能（通知はホーム画面追加時のみ、ウィジェットはネイティブアプリの構想でしかなかった）で、実装のない画面を残す理由がなかった。

## 技術方針

- **クライアントサイドのみで完結する。診断結果・チェック状況・台帳の内容は一切送信しない。** ただし診断のため、IPアドレスが `ipwho.is` / `ipify.org` / `www.cloudflare.com` / `edns.ip-api.com` / トラッカー遮断テストの接続先（Google・Meta・Criteo・Taboola）へ渡る。何がどこに渡るかは各カードのバッジと画面冒頭の説明文に明記する（「外部依存を隠さない」を参照）。
- **ノーログ方針。何も永続化しない。** `localStorage` への書き込みを一切行わない（詳細は「ノーログ方針：状態は一切永続化しない」を参照）。過去のバージョンにあった端末内保存は廃止した。
- **自動で設定を変更しない。** 気づかせるだけで、変更は本人の手で行わせる（Jumbo Privacyの教訓）。
- 配信元URL（`REMOTE_URL` 定数）を書き換えて git push するだけで、全ユーザーに新着項目が自動反映される。手動貼り付けは廃止した。

## ホスティング

静的ファイルを置くだけで動く。`main` への push で `.github/workflows/pages.yml` が走り、`settings-data.json` を検査したうえで GitHub Pages へ配信する。

**初回だけ手動の設定が要る。** Settings → Pages → Source を「GitHub Actions」にする。Actions のトークンには Pages サイトを新規作成する権限が無く、ワークフロー側からは有効化できない（`Resource not accessible by integration` になる）。なお **private リポジトリの Pages は GitHub Pro 以上が必要** で、無料プランならリポジトリを public にする。それまでは `deploy` ジョブだけが失敗し、`validate` ジョブは通常どおり通る。

他のホスティングに置く場合も、`index.html` / `support.js` / `settings-data.json` を同じディレクトリに並べるだけでよい（`.nojekyll` 同梱）。

`file://` で直接開くと `settings-data.json` の取得がブラウザにブロックされるが、その場合は内蔵データのまま静かに動作する。動作確認はHTTP経由で行うこと。

```
python3 -m http.server 8000
# → http://localhost:8000/
```

## 項目を追加・更新する

1. `settings-data.json` を編集する
2. `version` を必ず上げる（例：`2026-07-30a` → `2026-08-05a`）
3. commit して push

次回起動時、`version` の差分を検知して各端末のデータが差し替わり、増えた項目は「新着」タブに `NEW` として並ぶ。
既存項目の `id` は変えないこと。`id` はセッション内でチェック状況（`state.done` / `state.seen`）を結びつけるキーとして使われる（ノーログ方針のため `localStorage` は経由しないが、同一セッション中の対応関係はこのidで保たれる）。

項目のスキーマ:

```jsonc
{
  "id": "line-talkroom-info",        // 一意。後から変更しない
  "title": "トークルーム情報の提供をオフ",
  "path": "設定 → プライバシー管理 → 情報の提供 → トークルーム情報",
  "severity": "high",                // high | medium | low
  "why": "なぜ重要か・既定値はどうなっているか",
  "watch": "既知の不具合など（任意）",
  "verifiedAt": "2026-07-29"         // この内容を実機で確認した日
}
```

アプリ側のスキーマ:

```jsonc
{
  "id": "line",
  "name": "LINE",
  "icon": "L",
  "category": "app",   // os | app | service。初回選択画面の分類に使う
  "items": [ /* ... */ ]
}
```

`index.html` 内の `APP_DATA` は、配信元に到達できない場合のフォールバックとして残している。大きな改訂のときは両方を揃えておくとよい。`version` は両方同じ値にしておく。

配信データのトップレベルには `minVersions`（`{ios, safari}`）も置く。「OS・ブラウザの更新状況」の判定基準として使われる。新しいiOSが出たら、ここを上げるだけで全端末の判定が更新される。

## ネイティブアプリ化は見送り

ノーログ方針への転換に伴い、iOSネイティブアプリ化で検討していた機能の多くが前提を失った——Keychain保管対象（何も持たない）、バックグラウンド定期実行の根拠（「前回との比較」自体が存在しない）、ウィジェットの表示内容（同上）。証明書検証・Tor検知等の専門的なネットワーク診断項目の追加も含め、現状は見送り、GitHub Pagesでの静的Web配信を継続する。

## 既知の制約

- **iOSはサードパーティによるインストール済みアプリ一覧の自動取得を許可しない。** そのため初回に、使っているサービスを手動でチェックリストから選ばせる方式にしている。
- **`support.js`（Claude Design ランタイム）は `new Function()` と外部CDN（unpkg）への動的依存を持つ。** 厳格なCSP環境（Claudeのファイルプレビュー等）では正しく動作しない。実機・実際にホストした環境での動作を前提とする。
- ネットワーク診断のうち **「アプリ間の追跡許可」「VPN接続の確定判定」「ウィジェット」はiOSネイティブAPI（`ATTrackingManager` / `NWPathMonitor` / `WidgetKit`）が前提** で、Web版に代替手段はない。UIでは端末側で確認する手順を案内している。
- **iPhoneのSafariはタブで開いている間は通知APIを持たない。** ホーム画面に追加したWebアプリとして起動した場合のみ、iOS 16.4以降で通知が使える。テスト通知のダイアログでその手順を案内している。
- DNSリーク検査で分かるのは、実際に問い合わせを行った**1つのリゾルバ**だけ。全リゾルバの列挙は権威DNSサーバー側のログが必要で、静的ページでは実施できない。網羅的に見たい場合はブラウザで dnsleaktest.com を直接開く（チェックリスト側にも項目として入れてある）。
- `edns.ip-api.com` / `ipwho.is` / `api.ipify.org` / `cloudflare.com` は外部サービスで、仕様やCORSポリシーが変われば該当項目だけ「確認できませんでした」になる。他の項目や画面全体には影響しないよう個別に例外処理している。**材料不足を警告として表示しないこと。** 漏れていないのに漏れて見えるのは、このツールでは最悪の失敗。
- ブラウザからは本来の traceroute を実行できないため、「出口ノード」は到達しているネットワーク結節点を代替指標として表示している。
- 「トラッカー遮断の実測」は `mode:'no-cors'` でリクエストを投げ、レスポンス本文は読めない前提で「reject されたか（=遮断）／resolve したか（=通過）」だけを見る。7秒でタイムアウトし、その場合は「遮断」でも「通過」でもなく「判定不能」として扱う——タイムアウトを遮断側に倒すと、回線が不安定なだけの状況を過大に「安全」と表示してしまう。
- 「ブラウザ指紋の識別性」はローカルで計算したハッシュを表示するだけで、どこにも送信しない。指紋の強さの目安は「取得できた信号の種類数」であり、実際の追跡可能性を測る指標ではない。
